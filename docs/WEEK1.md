## 依赖和合并顺序

1. C 当天在 `docs/API.md` 冻结 `batch_id`、`batch_code`、时间、公开字段和错误码；A/B 按契约交请求响应样例。字段争议当天在 issue 记录并由 C 更新文档。
2. 先合入数据库及批次 API，再合入页面；A 的模型服务与 B 的规则模块可以并行开发，不阻塞批次纵切验收。
3. 所有变更从 feature 分支发 PR 到 `develop`；至少一名其他成员复核接口字段、运行方法和样例。`main` 暂不接收功能提交。

## 9/26 验收清单

- [ ] 三人的机器均可 clone、安装依赖，并按部署文档启动已完成的服务。
- [ ] `APPLE-2026-001` 在数据库中只有一条，所有子记录由 `batch_id` 关联。
- [ ] 首页与批次列表从后端取得同一批次，不写死指标或检测结果。
- [ ] `/trace/APPLE-2026-001` 只返回公开事件；质检、加工、冷链尚未执行时显示“暂无记录”。
- [ ] A/B 的 JSON 契约、数据来源与模拟标识均可复核；模型占位输出有 `stub` 标记。
- [ ] 至少一轮成员间 PR review 完成，保留三机运行截图、接口样例和未解决问题清单。
